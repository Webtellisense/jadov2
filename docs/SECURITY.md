# M0 security boundary

M0 is a local foundation, not a production launch. Public registration, password recovery, email OTP, Google sign-in/GBP authorization, business activation and paid providers are unavailable.

Better Auth owns password hashing and credential sessions. The public route exposes only credential sign-in, session read and sign-out. Credentials are not put in localStorage or URL parameters. Session cookies are HttpOnly and SameSite=Lax; production uses Secure cookies and requires HTTPS APP_ORIGIN. Account linking is disabled; OAuth tokens will be encrypted if a later approved provider is configured. Cookie caching is disabled so account state is checked against PostgreSQL on each application request. Expired, revoked, suspended and development-only production sessions are denied.

Role, account state and fixture markers are server-owned. A platform administrator does not automatically gain business rights. Business access requires an active membership and verified-active business; M0 has no activation endpoint or manual verification shortcut. Tests that exercise that predicate use labeled records only in isolated test databases.

The single application mutation is the signed-in user's own display name. It requires the configured Origin, a bounded JSON body, a strict schema, an active account rechecked under a row lock, a PostgreSQL per-user rate limit (10/minute), and a transactional audit entry. Audit entries contain identifiers and action names, not old/new names or credentials. Better Auth separately limits credential sign-in attempts to five/minute and uses PostgreSQL for counters. In production, the reverse proxy must sanitize client IP headers before forwarding traffic; accepting arbitrary forwarded IPs would weaken IP-based auth rate limits. Per-account limits and abuse detection for public registration are future work before launch.

The health endpoint returns no database address, version, credentials or error stack. Known application errors return safe messages; unknown errors return a generic 503 with a generated request ID. Error logs contain only an event name and correlation ID. PostgreSQL pooling is bounded to five connections per process, with connection timeouts. Production credentials should be least-privilege, migrations should use a separate database role, and remote database TLS must follow the provider's verified trust configuration.

Development seed requires an explicit opt-in, loopback host and a jado_dev/jado_test database name. It refuses NODE_ENV=production, marks every fixture, creates no verified business or membership, and supports targeted reversal. Production session creation and protected app routes reject fixture users. The cloud database uses passwordless trust authentication on host loopback only; this Compose configuration must never be deployed to production. Seed passwords and the auth secret are generated into ignored .env with mode 0600 and never printed by setup. Use normal secure environment settings for production; do not share .env or test traces publicly.

No network transport exists in M0 provider adapters. Disabled flags return DISABLED, missing/zero caps return BUDGET_NOT_APPROVED, and enabled positive-cap settings still return NOT_IMPLEMENTED. There is no success fallback for Google verification or AI. Domain, provider costs, API approvals, retention schedules, real consent/privacy text, backup restore drills, and full abuse controls must be resolved in their milestones before release. Auth sessions have an eight-hour TTL; audit/rate-limit cleanup needs a scheduled retention job before production traffic, not an always-running worker.
